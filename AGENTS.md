# PreAce-lite — project notes

## Stack
Node.js + Hono (web) + Drizzle ORM + Postgres + Eta templates. Single-process.
- Entry: `src/index.js` — boots web server, runs migration, optionally starts engine (`RUN_ENGINE=false` to disable price-polling/engine worker).
- DB client: `src/db/client.js` exports `db` (drizzle) and `sql` (raw tagged template via postgres).
- Migrations: `src/db/migrate.js` (idempotent `create table if not exists` style). Run with `node src/db/migrate.js`.
- Seed: `src/db/seed.js` creates admin (`admin@preace-lite.com`) + demo client + plans/traders/prices.
- Auth: `src/lib/auth.js` — cookie session (`rr_sid`), CSRF token = HMAC of session id (stable per session), `csrfGuard` middleware on all POST/PUT/PATCH/DELETE.
- Views: `src/lib/view.js` — Eta render. Templates in `src/views/`. Layout wraps inner body via `<%~ it.body %>`.
- Static assets: `public/` (js/app.js, css).

## Key conventions
- All forms include `<input type="hidden" name="_csrf" value="<%= it.csrf %>">`.
- Eta raw output uses `<%~ %>` (needed for JSON in data attributes; `<%= %>` HTML-escapes).
- Admin routes in `src/routes/admin.js`, user routes in `src/routes/dashboard.js`.
- Login diagnostics: failed logins are logged server-side (`[auth] login failed (no such user|bad password)`) while the UI stays generic — check app logs before touching the DB. Account recovery: `ADMIN_PASSWORD='New!123' npm run reset-admin` (creates or resets the admin; see `src/db/reset-admin.js`).
- "Your session expired" 403 = `csrfGuard` token mismatch (not an expired DB session — tokens are HMACs of the cookie's session id, stable for the session's life). Causes: stale tab after sign-in/out elsewhere, browser-back resubmission, or SESSION_SECRET changing between GET and POST. Rejections now log `[csrf] rejected ...` and render a friendly page that links back to the Referer (fresh token on reload). All form POSTs are plain HTML forms (no fetch/htmx mutations); every GET page renders a valid `_csrf` — verified by scanning rendered HTML.
- Mail: `src/lib/mail.js` renders `.eta` body wrapped by `views/mail/layout.eta`, logs to `mail_log` table, sends via nodemailer SMTP. `getTransporter()` reads `mail_config` from `settings` table first, then `SMTP_URL` env, else log-only. Fire-and-forget with `.catch()`.
- Settings: `src/lib/settings.js` — key/value store in `settings` table (jsonb). Wallet addresses stored under key `wallet_addresses`. Site-wide knobs (`supportEmail`, `smartsuppKey`) under `site_config` via `getSiteConfig()`/`setSiteConfig()` — cached 15s in-process, safe before migration (falls back to defaults); `render()` exposes it to templates as `it.site`.
- Support/contact: support inbox defaults to `preacelitesupport@gmail.com` (env `SUPPORT_EMAIL`, editable at `/admin/site`). Contact form POST forwards to it via `mailContactMessage`. Mail settings Gmail preset is prefilled with that address — admin only pastes the App Password.
- Smartsupp chat: widget key lives in `site_config.smartsuppKey` (env `SMARTSUPP_KEY` fallback), editable at `/admin/site`. Layouts render the widget only when the key is set; it is never rendered on admin pages (`layouts/admin.eta` has none; auth layout suppresses it on `/admin/login`; app layout skips it for admin role).
- Admin console separation: admin uses its own `src/views/layouts/admin.eta` (no user links, no balance chip, no chat). Staff sign-in is `/admin/login` (admin-role only, generic error otherwise); `requireAdmin` redirects unauthenticated hits there and 404s non-admins. Admin nav active state uses longest-prefix matching (`activeHref` computed in the admin `shell`). Raw `sql` rows are snake_case — map to camelCase (`first_name` → `firstName`) before passing to mail helpers.
- Admin compose: `/admin/mail/compose` (System → Send mail) sends to one user or broadcasts to all active users via `mailAdminMessage(u, subject, message)` (plain text; paragraphs pre-escaped in the helper, template emits raw). Registered recipients also get an in-app notification. Entry points: nav, outbox "Compose mail" button, "Email this user" on the user page.

## Wallet dashboard + recovery snapshots (v3)
- **BalanceService** (`src/lib/balance.js`) is the single source of truth for what the dashboard renders. `getBalanceOverview(user)` returns `{ kind, displayTotal, approxcBtc, assets, real, snapshot, isRecovery }`. Kind is one of `real_balance` (ledger-derived), `recovery_display_balance` (user `account_class='recovery_test'` + snapshot), or `test_balance` (snapshot on a non-classified account). Snapshots NEVER write ledger/transactions — they are display data only.
- Recovery tables (migrate v3, also in schema.js): `user_balance_snapshots` (header: display_total numeric(20,8), btc_price, status draft|pending|verified), `user_balance_snapshot_assets` (asset, display_balance, display_quantity), `recovery_notes`, `recovery_investment_plan` (contribution_amount/frequency/duration_months/status='recovery_reference'/source='admin_recovery'). Users get `account_class` (`production`|`recovery_test`) + `recovery_status`.
- Seed (`src/db/seed.js`) creates Tammy Riley (id 3, email `tammy.riley@preace-lite.com`, class `recovery_test`) with snapshot #1: BTC $1365.80 / 0.021624, ETH $482.20 / 0.190196, USD $200.00, total $2048.00, and plan config $750 biweekly / 7mo (recovery_reference, no payments). `src/db/recover-tammy.js` is a standalone idempotent restorer.
- **Recovery console** (`/admin/recovery`, admin-only; block lives in `src/routes/admin.js` around line 580): search by name/email/id returns the account under `it.target` in `src/views/admin/recovery.eta` (DO NOT rename back to `user` — that collides with the admin shell's `c.get('user')`). Every mutation lives in `src/lib/recovery.js` (classifyAccount, createSnapshot, verifySnapshot, addRecoveryNote, upsertInvestmentPlanConfig) and writes an `audit_log` row in the same txn.
- Wallet dashboard UI: `src/views/dashboard/home.eta` + `src/views/partials/wallet/` (balance-header, quick-actions, asset-card, asset-row, market-overview, market-asset-row, referral-card). Built as an Eta component system, no new framework. Visibility toggle + user menu + referral dismiss in `public/js/app.js` (localStorage key `w_hide_balance`; server always renders full amount, JS masks client-side only).
- Active/recovery marking: users with `account_class='recovery_test'` see an admin-only style banner ("Recovery / test account") + Activity/Portfolio pages label snapshot totals as recovery display data. Ordinary customers (class `production`) never see it; snapshot display never touches their ledger.
- Trade page `/dashboard/trade` accepts `?action=buy|sell` and `?sym=BTCU|BTC` etc. (quick-action links use `?action=buy|sell` and market rows use `?sym=PAIRUSDT`); template binds `it.action` (defaults buy) and `it.sym` (defaults BTCUSD).

## Frontend conventions & gotchas
- Auth pages (`layouts/auth.eta`, `layouts/site.eta`, `layouts/app.eta`) include `<script src="/js/app.js" defer></script>` — it drives the mobile nav, side drawer, balance visibility toggle, and referral-card dismiss. Forms are plain HTML POSTs (no fetch/htmx mutations) with a valid `_csrf` on every render.
- Inner page templates are rendered via `eta.render(view, {...})` into `body` BEFORE `render()` wraps the layout — so `csrf`/`user` injected by `render()` do NOT reach the inner template. Every inner render of a form template must pass `csrf: c.get('csrf')` explicitly (admin.js/dashboard.js do; public.js SIMPLE pages + contact POST were missing it → `_csrf` rendered as literal "undefined" → 403 "session expired").
- `public/css/app.css` carries two naming layers: a BEM-style layer (`.stat__v`, `.card--flush`, `.btn--ghost`) and a "single-dash" compatibility layer (`.stat-v`, `.btn-ghost`, `.card-head`, `.metric-card`, `.notice`, `.page-head`, `.kv`, `.meter`, `.avatar`, `.trader-head`, `.plan*`, `.row2`). The `.eta` dashboard templates use the single-dash names; both resolve onto the same design tokens. Keep new component styles in the single-dash layer to match the templates.
- Dashboard tables use bare `<table>` inside `.table-wrap` (NOT the `.tbl` class). Styles live under `.table-wrap table` so they apply automatically — no need to add a class in templates.
- Sidebar (`.side`) is a sticky column on desktop (`@media min-width 901px`) and a fixed off-canvas drawer on mobile (`@media max-width 900px`). The drawer is driven by `public/js/app.js`: `[data-side-toggle]` opens, `.scrim`/`.side-close`/ESC/nav-link click close, and `body.side-open` locks scroll. Breakpoint is 900px; a tablet refinement exists for 901–1100px.
- Horizontal-overflow gotchas caught by the mobile audit: `position:fixed` off-canvas drawers (`nav-links`, `.side.open`) contribute to `documentElement.scrollWidth` even when `transform:translateX(100%)` — set `display:none` when closed or `overflow-x:hidden` on an ancestor. `.auth-glow` on login/register is decorative 760px — clamp its width with `min(760px,100vw)`. `--ff-display` vs `--f-display` typo broke 7 templates' display headings (`sed 's/--ff-display/--f-display/g'`). `.main{overflow-x:hidden}` prevents a wide card/table from scrolling the app shell sideways.

## Withdrawal cycle-hold (all account classes)
- **Hold gate**: `investmentCycleHold(userId)` in `src/lib/balance.js` returns a `cycle` object when the user has an **active** `investments` row on a fixed plan whose `matures_at` is in the future — **for every account class** (`production` and `recovery_test` alike). `null` = withdrawals allowed.
- **Recovery/ref-only accounts** (`recovery_test` with no `investments` row but with a `recovery_investment_plan` reference): `recoveryReferenceHold(userId)` in `src/routes/dashboard.js` (fallback called after `investmentCycleHold` in GET `/dashboard`, GET `/dashboard/withdraw`, and POST `/dashboard/withdraw`) synthesizes a cycle from the reference plan (7-month, $750 biweekly for Tammy) — withdrawals stay held until a real investment lands and matures.
- **Order matters**: POST fires the hold guard **before** balance/method checks so a snapshot-only recovery balance never gets a confusing "insufficient funds". Recovery accounts remain **bank-only** (`method.type==='bank'`) + selfie URL required inside the hold block; production accounts keep all enabled methods.
- `cycle` (mirrored with `active: !matured`) drives both the home banner and the withdraw notice/modal (`it.cycle.message`); the modal renders only when `it.prev` exists (POST round-trip. Period label: plans `<62` days show `N-day`; longer show `N-month`.

## Testing locally
Needs Postgres. Start one, set `DATABASE_URL` in `.env` (use `?sslmode=disable` for a local container — `postgres` lib defaults to SSL `require`), run `node src/db/migrate.js && node src/db/seed.js`, then `RUN_ENGINE=false node src/index.js`.
- CSRF note for curl: fetch the page with the cookie jar, grep the `_csrf` token, POST with the same jar. Token is stable per session.
- No CAPTCHA (reCAPTCHA was removed entirely — no frontend Google script, hidden `g-recaptcha-response` inputs, server-side verification, or related CSP entries). Login/register/admin-login/contact rely on CSRF + login throttling (`throttle()` in `lib/auth.js`) instead.

## Deployment (Railway)
- `railway.json` (DOCKERFILE builder) + `Dockerfile` (node:22-slim, builds argon2 native binding). `.dockerignore` excludes node_modules/.env/.git/public/uploads.
- **Auto-deploy: the Railway service is connected to the GitHub repo — every push to `main` triggers a build + deploy automatically.** No manual step. If a push does NOT trigger a build, the repo↔service link is broken: re-connect it in Railway dashboard → service → Settings → Source, or enable "Auto Deploy". Verify a deploy landed by hitting `/healthz` and checking Railway logs.
- App runs migration on boot (background, non-fatal) so `npm run migrate` is optional. `/healthz` = liveness (no DB), `/readyz` = readiness (DB probe). Docker HEALTHCHECK hits `/healthz`.
- `PORT` injected by Railway. Required vars: `DATABASE_URL`, `SESSION_SECRET`, `ADMIN_EMAIL`, `ADMIN_PASSWORD`. Optional: `UPLOAD_DIR`, `SMTP_URL`/`MAIL_FROM`.
- DB providers: plain Postgres only, no provider-specific features. Neon → pooled `-pooler` host. Supabase → **Supavisor session pooler** (`aws-0-<region>.pooler.supabase.com:5432`, user `postgres.<ref>`); the direct `db.<ref>.supabase.co` host is IPv6-only and unreachable from Railway; transaction pooler (6543) works but session mode is safer. Client already runs `prepare: false` for pgbouncer compatibility. Migrate data with `pg_dump --no-owner -Fc` + `pg_restore`, then swap `DATABASE_URL` (see README "Moving an existing database").
- Receipt uploads: saved to `UPLOAD_DIR` (default `public/uploads`). Railway filesystem is ephemeral → mount a Volume at `/data` and set `UPLOAD_DIR=/data/uploads` or receipts vanish on redeploy. Dir is auto-created on boot (before static routes register). Served at `/uploads/*` via serveStatic with rewriteRequestPath.
- Mail/SMTP: the **built-in web mail** is the default (`provider: 'builtin'` in `settings.mail_config`) — no external provider; messages are recorded in the admin outbox (`mail_log`) and users get in-app notifications. Auto-written at boot by `autoSetupMail()` when nothing is configured. Optional external delivery: `SMTP_URL` or discrete `SMTP_HOST/PORT/USER/PASS` env (written once at boot), or System → Mail settings (admin UI saves always win; saving clears the env-managed marker). Gmail: smtp.gmail.com:465 SSL + App Password.
- Live chat (Smartsupp): widget snippet lives in ALL four layouts (`site`, `app`, `auth`, `admin`) — active on every page when `site_config.smartsuppKey` is set (System → Site settings). CSP `script-src`/`connect-src` whitelist `www.smartsuppchat.com` (+ `wss:`); removing it from CSP breaks the widget silently.
- Payment methods: dynamic `payment_methods` table. Admin CRUD at **System → Payment methods** (list + per-method edit `<details>` blocks, shared form partial `views/partials/pm-form.eta`). Per-method: type (crypto/bank/mobile/giftcard/gateway/manual/other), deposit/withdrawal enable flags, min/max deposit+withdrawal, fixed+percent fees, deposit/withdrawal instructions, dynamic required fields (JSON `[{name,label,type,required,placeholder,help}]`, max 20), sort order, archive. `listPaymentMethods(enabledOnly, 'deposit'|'withdrawal')`. Delete archives (not deletes) when transactions reference the method. Eta gotcha: no regex literals containing quotes, and no multi-line expressions inside `<%~ %>` raw tags.
- Ledger buckets: `main | profit | bonus | ref_bonus | deposit | locked`. `balance()` in stats.js returns all; `available = main+profit+bonus+refBonus` (locked & deposit excluded from withdrawable). Admin credit/debit: `src/lib/finance.js` `creditDebit()` — SQL transaction, ledger + audit_log + notification commit together; debits can't go negative. Two-step confirmation: POST without `confirm=1` redirects back with `?cd=confirm&...` staging params; the page renders the confirm block with before/after.
- Audit: `audit_log` table + `/admin/audit` page. Logged actions: credit/debit/clear_account, deposit/withdrawal approve+reject, withdrawal_processing, reset_password, withdrawal_code_set/clear, impersonate, delete_user.
- Withdrawal code: `users.withdrawal_code_hash` (argon2 hash, plain code shown once to admin). If set, withdraw requires it.
- Withdrawal flow: `POST /dashboard/withdraw` two-step (confirm page `withdraw-confirm.eta` shows amount/fee/net/min); fees = fixed + percent computed in integer cents; hold via ledger `withdrawal_hold` at submit, released on reject. Statuses: pending → processing → approved (complete) | rejected. KYC gate: `site_config.withdrawalKycRequired` toggle at System → Site settings.
- Admin user page (`/admin/users/:id`): financial summary cards (5 buckets + portfolio), Actions (credit/debit, withdrawal code, notify, login-as-user `createSession` + audit, reset password (admin types the new password — min 8 — into a prompt; user is signed out everywhere and gets a security notice mail with NO password in it), ban/suspend, clear account, delete — delete blocked when ledger history exists), recent transactions, login activity (sessions).

## Mobile audit hardening (320/375/414/768/1024+) — 2026-08
- **Market rows ≤399px**: `.w-market` name/ticker column used to collapse to ~13px because the fixed 76×28 sparkline + 86px price min-width left nothing. Fix: `@media (max-width:399px)` block in `app.css` shrinks the vector sparkline to 42×16 (`viewBox` scales) and tightens row gaps so name/ticker keep 73–84px. Full-size spark (76×28) returns at 414px+.
- **Touch targets**: tiny wallet icon buttons keep their subtle 20–28px visuals but gain a ≥40px hit area via a positioned pseudo-element: `.w-ico-btn::after{inset:-8px}`, `.w-ico-btn--xs::after{inset:-10px}`, `.w-referral__close::before{inset:-9px}`. `.btn-sm` gets `min-height:42px; padding-block:10px` and `.w-action__btn` 56×56 under 900px.
- **User-menu shadow**: `.w-usermenu__panel` references `--w-shadow-pop` — the token must exist in the wallet token root (`.app{...}`) or the menu has no shadow. Token added.
- **Login rate limiter gotcha for test scripts**: `throttle()` in `lib/auth.js` is an in-memory map (max 8 POSTs / 5 min, keyed on `x-forwarded-for` or `'local'`). Repeated automated login POSTs from fresh Playwright contexts quickly hit **429** and stay blocked for 5 min. Clearing it requires restarting the server (`kill <pid>` then start again). Playwright probes should reuse one authenticated context or batch work in bursts < 8 logins.
- **Audit tooling**: playwright-core is only in `/tmp/pw` (project has no test deps). Login helper `/tmp/pw/login-helper.js` handles the CSRF flow and retries 3×; `audit.js`/`final-audit.js` produce per-viewport JSON (scrollW/overflowX/clipped/smallTargets). Chromium at `/usr/bin/chromium`.
- **No page overflow** at 320–1440 across /dashboard, activity, learn, portfolio, markets, trade, invest, deposit, withdraw, statement, admin, admin/users, admin/recovery, admin/audit. Residual `clipped` entries on dashboard are the intentional pseudo-element hit-area overlays (not visual bugs).
